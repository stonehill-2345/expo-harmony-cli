# expo-harmony-cli 1.0.0 实现技术方案

> 目标版本：1.0.0
> 当前基线：Expo SDK 52 / React Native 0.77.1 / RNOH 0.77.71
> 目标：稳定“从 0 创建 Expo + HarmonyOS 基线”的主链路
> 范围：正确性、配置安全、端口统一、依赖适配和现有 Release bundle 稳定化

## 1. 目标与非目标

### 1.1 目标

完成以下链路并保持幂等：

```text
create -> install -> prebuild --platform harmony -> sync -> start:harmony -> bundle:harmony:release
```

用户完成 `prebuild` 后，可以在 DevEco Studio 打开 `harmony/` 继续开发和构建。普通 Expo/iOS/Android 配置不被 CLI 静默破坏。

### 1.2 非目标

本版本不实现：

- `build-hap` 自动构建和签名托管；
- 存量项目 `migrate`；
- `doctor`、完整 `env`、JSON 报告；
- plan/apply 事务回滚和 Capability Registry 重构；
- Expo 55/RNOH 0.82 升级；
- npm registry、Gitee 镜像或下载加速逻辑；
- CDN 模板和 Hermes HBC。

## 2. 现状问题与设计决策

| 问题 | 当前行为 | 1.0.0 决策 |
|---|---|---|
| shell 参数 | installer/uninstaller/prebuild 使用命令字符串 | 全部外部命令改为 `runFile(file, args)` |
| codegen | TurboModule 路径固定执行 `pnpm codegen` | 复用 `resolvePm`，按 pm 生成脚本命令 |
| Metro 配置 | injector 无条件写 `metro.config.js` | 共享配置按 `RN_BUNDLE_PLATFORM` 分支，已有文件不静默覆盖 |
| Metro 端口 | HarmonyOS 固定 8888，Expo 默认 8081 | 默认统一 8081，支持 `HARMONY_METRO_PORT` 覆盖 |
| autolinking | 仅检查 npm 包目录，可能生成虚假注册 | 校验 HAR、ArkTS、C++、CMake 入口，缺失时失败或 skipped |
| scan | 默认直接修改 package、patch、alias | 默认只读预览，`scan --apply` 才写入 |
| release bundle | 已有注入脚本，但需加强配置和陈旧产物保护 | 保留脚本入口，清理旧产物并校验非空产物 |

## 3. 技术设计

### 3.1 参数化命令和包管理器

在 `src/lib/pkg-manager.ts` 定义统一命令结构：

```ts
export interface CommandParts {
  file: string;
  args: string[];
}
```

命令映射：

```text
install:  pnpm -> pnpm install；npm -> npm install；yarn -> yarn；bun -> bun install
remove:   pnpm -> pnpm remove；npm -> npm uninstall；yarn -> yarn remove；bun -> bun remove
script:   pnpm -> pnpm <script>；npm -> npm run <script>；yarn -> yarn <script>；bun -> bun run <script>
```

`resolvePm` 维持“显式 flag > lockfile > pnpm 默认”的优先级。所有调用点通过 `runFile` 执行；`run()` 保留用于未迁移的历史路径并标记 deprecated。

受影响模块：

- `src/utils/exec.ts`
- `src/lib/pkg-manager.ts`
- `src/installer/installer.ts`
- `src/installer/uninstaller.ts`
- `src/commands/prebuild.ts`

### 3.2 共享 Metro 配置安全合并

不新增强制独立 Metro 配置文件。保留一个项目级 `metro.config.js`，将 HarmonyOS 逻辑封装为条件分支：

```js
const isHarmonyBundle = process.env.RN_BUNDLE_PLATFORM === 'harmony';
module.exports = isHarmonyBundle
  ? mergeHarmonyConfig(userOrExpoConfig)
  : userOrExpoConfig;
```

写入策略：

1. 新项目没有 `metro.config.js` 时，生成 CLI 默认共享配置。
2. 已有配置时，先识别是否为 CLI 生成内容。
3. CLI 管理内容可安全更新；用户自定义内容不得整体覆盖。
4. 无法安全合并时中止并提示用户手工合并，不生成半成品。

HarmonyOS 分支继续提供：RNOH resolver、shim alias、`@/` alias、SVG transformer、Expo Router root 设置。普通平台分支继续走 Expo 默认配置。

受影响模块：

- `src/injector/metro-config.ts`
- `src/injector/index.ts`
- `src/injector/bundle-harmony-release.ts`
- `src/injector/bundle-harmony-dev.ts`
- `src/injector/start-harmony.ts`

### 3.3 Metro 端口统一

新增模板脚本统一端口解析：

```js
const DEFAULT_METRO_PORT = '8081';
const metroPort = process.env.HARMONY_METRO_PORT || DEFAULT_METRO_PORT;
```

同步使用 `metroPort`：

- `expo start --port <metroPort>`；
- `EntryIndex.ets` 默认 Dev Settings 地址 `localhost:<metroPort>`；
- `hdc rport tcp:<metroPort> tcp:<metroPort>`；
- 日志和错误提示；
- 文档和测试断言。

端口不是 bundle 产物的一部分。Release 模式生成 rawfile 后，关闭 Metro 和端口转发仍必须可启动。

### 3.4 autolinking 真实性校验

`runAutolinking` 在生成注册文件前，对每个 mapping entry 做路径校验：

- npm 包目录存在；
- `harName` 对应 HAR 存在且为非空文件；
- ETS import 对应入口存在；
- C++ package 对应头文件/源码存在；
- CMake library 目录或 `cppSourcePath` 存在。

结果扩展：

```ts
interface AutolinkingResult {
  linked: string[];
  skipped: Array<{ package: string; reason: string }>;
  files: Array<{ path: string; content: string }>;
}
```

对于缺失入口的原生包，默认阻断并输出包名、路径和修复建议；只有明确属于可选能力时才进入 `skipped`，禁止生成空注册后报告成功。

### 3.5 scan 只读/apply 分流

将 `scanAndAdapt` 拆分为“计算计划”和“应用计划”两个阶段，保持兼容表逻辑单一：

```ts
const plan = scanProject(projectRoot);
if (args.includes('--apply')) applyScanPlan(projectRoot, plan);
else printScanPlan(plan);
```

只读模式不得写入：`package.json`、patch、shim、alias map、managed-state。`--apply` 才执行现有修改流程。保留旧报告结构，新增 `wouldChange`/`drift` 信息。

### 3.6 Release bundle 稳定化

保留项目脚本入口 `bundle:harmony:release`，不在 1.0.0 新增统一 `bundle` CLI 命令。

脚本步骤：

1. 校验 `harmony/entry` 和 `@react-native-community/cli`；
2. 删除旧 `bundle.harmony.js` 和 `assets/`；
3. 调用 `react-native bundle-harmony --dev false --entry-file index.harmony.js`；
4. 传递 `RN_BUNDLE_PLATFORM=harmony`，使用共享 Metro 配置；
5. 校验 bundle 存在、非空，assets 目录可用；
6. 输出 rawfile 路径和 DevEco 下一步提示。

失败时返回非零退出码，不能保留可被误用的旧产物。

## 4. 实施顺序

### Phase 1：命令执行基础

- 先补 `pkg-manager`、`exec` 和四种包管理器测试；
- 迁移 installer/uninstaller/prebuild 调用点；
- 增加 TurboModule codegen 映射测试；
- 运行 type-check 和相关单测。

### Phase 2：Metro 与端口

- 先为 `metro-config` 补“已有配置不覆盖”失败测试；
- 实现共享配置的 HarmonyOS 条件合并；
- 将端口常量注入 start、EntryIndex、hdc rport 和文档；
- 验证默认 8081 与自定义端口。

### Phase 3：autolinking 与 scan

- 为缺 HAR/ETS/C++/CMake 入口补失败测试；
- 实现 `skipped`/blocker 结果和稳定错误信息；
- 将 scan 改为默认计划输出，新增 `--apply` 测试；
- 验证重复 apply/sync 幂等。

### Phase 4：bundle 与发布验收

- 补 release bundle 脚本的 stale/空产物测试；
- 验证共享 Metro 配置和 8081 端口；
- 执行 npm pack 内容校验；
- 执行 create→install→prebuild→sync 冒烟。

## 5. 测试方案

### 单元测试

- `exec.test.ts`：特殊字符参数、Windows `.cmd`、命令数组；
- `pkg-manager.test.ts`：install/remove/script 四种 pm 映射；
- `install.test.ts` / `uninstall.test.ts`：codegen 使用实际 pm；
- `injector.test.ts`：Metro 不覆盖用户配置、Harmony 分支和端口；
- `autolinking.test.ts`：入口缺失阻断、skipped、输出稳定；
- `scan.test.ts`：默认只读、`--apply` 才写入、重复 apply；
- `bundle` 脚本测试：旧产物清理、空产物失败、成功产物路径。

### 集成验收

在 macOS 主环境执行：

```text
create -> install -> prebuild --platform harmony -> sync -> start:harmony -> bundle:harmony:release
```

Windows 至少执行命令解析和 dry-run 测试；真实 DevEco/HAP 构建不作为 1.0.0 阻断条件。

## 6. 回滚与兼容策略

- 每个 Phase 保持独立提交边界，失败可回退单个 Phase；
- Metro 配置无法安全合并时拒绝写入，不覆盖用户文件；
- 端口统一保留 `HARMONY_METRO_PORT`，旧项目可临时使用 `8888`；
- scan 默认行为变化提供 `scan --apply` 兼容入口；
- release bundle 失败删除本次目标产物，避免回退到 stale bundle；
- 不修改用户手工维护的 HarmonyOS 签名配置和非托管文件。

## 7. 完成定义

1. 全量单测和 type-check 通过；
2. create→install→prebuild→sync 冒烟通过；
3. 四种包管理器的 TurboModule codegen 行为通过测试；
4. HarmonyOS 默认 Metro 端口为 8081，端口覆盖可用；
5. 用户已有 Metro 配置不被静默覆盖；
6. autolinking 缺入口和 bundle 缺产物时稳定失败；
7. npm pack 发布物包含运行时所需模板和 content 文件；
8. 不引入 npm registry/Gitee 下载逻辑，不自动构建或签名 HAP。
