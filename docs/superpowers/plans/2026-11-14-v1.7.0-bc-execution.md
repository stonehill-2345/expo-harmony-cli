# 1.7.0 B/C 收敛开发执行计划

日期：2026-11-14。计划版本：v1。状态：已编制；下列开发与验收任务尚未由本计划签收。

> 唯一版本范围依据：[1.7.0 支持范围与收敛交付计划](2026-11-14-v1.7.0-delivery-scope.md)。本文只分解执行，不扩大或缩小该范围。使用 writing-plans 整理；实施可使用 executing-plans，按角色顺序推进，不自动启动子代理、联系其他会话或提交代码。

## 1. 目标、优先级与边界

交付标准开发流程、首批明确能力及真实候选消费；不要求全量 M7/M8 完成。首批 API/选项支持表必须继承原 M4 必达及原样 default 依赖，不能按包名假定整包支持。

执行优先级：用户最新明确指令 → 收敛范围 → 本计划 → 本轮任务卡/支持表 → 历史材料。历史计划只提供技术事实、原有必达 ID、契约和证据，不可重新分派任务、扩大范围或改变角色。范围冲突按上述次序解决；仅实际边界歧义、专项禁止或需要新增承诺时请用户裁决，不重复询问已授权任务。

Must：收敛计划全部 Must 与其必要依赖。Should/Could/Won’t 不自动排入当前任务。相机、定位、数据库等不得因扫描发现未实现而扩入；首批真正依赖的最小能力须记录具体调用链。既有 Metro“先具体方案、未经确认不改产品/基线”限制继续有效。

SDK54/React 19.1.1/RN 0.82.1/RNOH 0.82.30，Node 22.20.0、pnpm 10.19.0、Python 3、DevEco SDK/HDC；不在本轮升级工具链。普通修复先复现测试再最小修复；不建立新的验证平台或进度系统。

## 3. 开工核对与轻量任务卡

两人每轮都先读收敛范围和本计划，随后执行只读现场核对：

```sh
git branch --show-current
git rev-parse HEAD
git status --short
node --version
pnpm --version
```

核对实际源状态与已有交付，不能因旧文档写“待实现”就重建已有工具。保留现有未提交代码，不 reset/stash/切分支/覆盖他人修改。B 执行共享 install/build/pack，C 在隔离消费者和固定只读源快照中验证。

每个交付切片只需在本人输出目录的 task.md 记录：本计划任务 ID、收敛计划 R1～R4 与具体 Must、修改文件、验收动作/预期、输入身份、结果/原件路径、未完成项。无需另建完整设计和 HTML。条目不能映射到 Must 或必要依赖时，不进入本轮实现。

## 4. 并行批次与交付卡

### 第一批：范围与可运行候选准备（立即并行）

**B-170-01：现有产品/候选盘点及 Metro 具体方案，对应 R1/R2。**

输入：当前工作树、旧冻结候选、最新 public-candidate/blockers 和产品失败原件。
落点：B 交付目录；确需修复时才进入 B 所属 release/产品代码。

- [ ] 核对已有 producer、安装与打包入口的实际能力，分别列“已有可用”“待验收”“真实缺陷”，不重建已完成能力。
- [ ] 输出 Metro 四条差异的实际源码/产物位置、复现、最小修复方案、需重打包集合及受影响测试；保持旧专项限制，未确认不修改该产品/基线。
- [ ] 复核首批模板和模块运行依赖，给 C 具体必要依赖及 API/选项证据；不等待 C 完成全部支持表才开展已有明确 Must。

退出：可审查的 Metro 决策材料和候选缺陷清单；等待专项确认只阻塞相关项。

**C-170-01：范围落表与未决拆分，对应 R1。**

输入：收敛计划、现有 scope-reviewed 原件、M4-A01～A07、原样 default 使用路径及 B 已有/本轮材料。
落点：docs/releases/v1.7.0-support.md；必要时修复现有范围/公开面工具及对应测试。

- [ ] 支持表逐项记录原 ID、包/API/属性/事件/插件选项、Must 来源或依赖链、验收案例、当前状态及证据。B 只读复核产品语义。
- [ ] scope incomplete 分成当前必达未决、必要依赖与后置 M7；输出范围差异，不修改旧 scope.complete 或历史结果。
- [ ] 仅重建输入变化或首批闭合缺失的关系；无关历史来源图不反复全量重跑。

退出：当前必达都有明确映射、未决有具体原因；后置不计完成，不能以范围裁剪掩盖原 M4 失败。

### 第二批：一条真实采集闭环（与第一批无依赖部分交错）

**B-170-02：动作与原件采集，对应 R2。**

落点：abc/b-export-other-captures.mjs、ai-e2e/device.mjs、schema.mjs、schemas/run-manifest.schema.json 及其已有测试。

- [ ] 复用 b-other-capture-handoff.md 的六项 caseCaptures 契约；选择首个环境可运行的 Other 场景，由 B 在 task.md 写定 case ID 和真实动作，C 对照既有断言。
- [ ] 设备可用时采集候选/HAP/target/bundle/PID/boot、安装与日志命令、截图/layout 原件，立即交接该切片，不等全矩阵。
- [ ] 缺历史材料直接按现契约重采，不伪造历史；无设备保留 BLOCKED_DEVICE，只做必要主机接口验证。

**C-170-02：独立消费与语义断言，对应 R2。**

落点：abc/c-verify-m4-captures.mjs、check-other-log.cjs、b-run-m4.mjs、ai-e2e/report.mjs/evidence.mjs 及对应测试。

- [ ] 在 B 采集前完成接口读取和已有负例核对；复用 Core 单应用与 Other 多应用路径，不另建合并应用或平台。
- [ ] 收到首个真实切片即核验身份、日志语义和视觉/布局效果；区分伪证据拒绝、工具误判、产品失败、原件缺失。
- [ ] 真实误判先复现测试再最小修复；每个视觉场景明确现有自动断言或有原件的人工复核方式，不能以可解码代替功能通过。

共同退出：同一场景从真实动作到独立判定完整贯通；随后逐场景扩展，接口字段冻结。合成测试通过不等于本退出条件通过。

### 第三批：首批真实缺陷收尾（按切片流水交接）

**B-170-03：产品修复与候选更新，对应 R3。**

落点：首批 packages、配置/生成与 CLI、模板、产品夹具和 release 工具。

- [ ] 当前候选逐项复验资源、字体、Sheet/Drawer/方向、default/Image、Core、Other；仅修仍可复现的首批失败，先失败测试再修复。
- [ ] 补齐标准命令、配置与模块增删、必要故障恢复；复用已实现机制，不扩为通用升级平台。
- [ ] 产品包变化后重新构建打包，交付改变的 hash、源码身份和受影响案例；仅 C 工具变化不重冻产品。无法形成正式 clean-source 时先给出可审查差异，不自动提交。

**C-170-03：逐切片验收，对应 R3。**

落点：现有独立消费者、公开面/设备校验及支持表。

- [ ] 先核候选来源/包/类型一致性，再重放原件和独立运行受影响案例；两种结果分开记录。
- [ ] B 占设备时做主机/来源复核；设备交接后执行独立实跑，未运行不签设备通过。
- [ ] 将问题带 task/case ID、命令、原件、期望/实际交回 B；已通过材料的输入身份未变且影响分析允许时复用，不要求无关历史全重建。

共同退出：首批专项无 FAIL/BLOCKED/NOT_RUN；当前必达公开关系闭合。无需等待无关 M7 或完整旧 V 自动化平台。

### 第四批：一次最终组合验收

**B-170-04：冻结候选、集成检查与性能采样，对应 R4。**

- [ ] 形成固定候选及只读源身份，运行真实打包/安装与锁重装；由 B 执行一次完整 pnpm check，交出命令日志、退出码和 skip 原因。
- [ ] 交付四个原样模板消费者与八个 Debug/Release 构建运行案例、自验原件；候选修复后按影响补跑，不能串用旧 PASS。
- [ ] 同机同工具执行既有配对性能采样，阈值完全沿用收敛计划；采样时双方暂停其他重 CPU/IO 工作。
- [ ] 完成用户文件保护、资源删除、冲突/中断恢复、错误设备、第三方模块/插件、SDK52 与受影响共享平台回归。

**C-170-04：独立最终验收与版本意见，对应 R4。**

- [ ] 用同候选在仓库外独立消费者完成 blank/default × npm/pnpm × Debug/Release；检查 Release 离线冷启动、资源、导航、reload/前后台，保留独立命令和原件。
- [ ] 复核必要安全/边缘、SDK52/共享路径回归及性能原件；对关键结果独立验证，不能只读取 B 的 PASS 摘要。
- [ ] 在 v1.7.0-acceptance.md 分别记录核心功能、安全边缘、真实候选实跑、最终验收、版本关闭意见；支持表只对真实通过项标已验收。

退出：全部新范围 Must 通过，历史 M7/M8 保持原状态；只建议交付本版本，不自动发布。人工设备验收有真实动作、身份、原件和复核即可按收敛计划记录，不冒充自动化 V 完成。

## 5. 交接与资源调度

最小交接：task/case ID、源 revision 与 dirty/文件 hash、候选 manifest/hash、工具身份、真实 argv/cwd/退出码、HAP/设备/进程身份、原件路径/hash、结果及下一动作。复用已有 JSON 格式，不新造一套 schema。

B 采集可交付切片 → C 校验/复跑 → B 修复真实产品缺陷 → C 只重验受影响项。缺材料只阻塞相应任务，双方继续已明确无依赖工作。双方从对方输出目录只读取材料；未经用户授权不发送跨会话消息。

同一分支不等于同一输入身份：B 是共享 install/build/pack 的唯一执行者；C 使用独立临时目录、固定只读快照和候选副本。正式检查期间禁止修改其输入快照。包 hash 变化后重新分析失效范围。

共享设备严格串行。B 先检查并在本人交接记录写 target、用途、占用/释放状态，C 确认释放后使用；若占用状态不明，先协调设备，不能争抢。性能期间双方停止重负载。此处用现有文件交接，不开发资源调度系统。

主机回归按需运行现有命令，例如：

```sh
# B：采集/schema 接口回归
node --test scripts/sdk54/__tests__/abc-b-other-captures.test.mjs scripts/sdk54/__tests__/ai-e2e-device.test.mjs scripts/sdk54/__tests__/ai-e2e-schema.test.mjs
# C：独立消费/语义回归
node --test scripts/sdk54/__tests__/abc-c-m4-captures.test.mjs scripts/sdk54/__tests__/abc-c-other-log.test.mjs scripts/sdk54/__tests__/abc-b-m4-runner.test.mjs
# B：集成批次一次完整检查
pnpm check
```

以上不替代真实设备或全部产品测试；按实际修改选择现有专项。旧“每轮完整 HTML、每轮全量构建、全历史图重建”不再执行。

## 6. 防漂移规则与状态

1. 每轮 task.md 必须写明本计划 B/C-170 ID 及收敛计划 Must；没有映射的新想法先列后续，不编码。
2. 范围新增/移除、断言放宽、必达转可选必须列原因、支持清单差异、影响及用户确认；普通范围内修复无需重复申请。
3. 历史“全量 M7/M8”“旧角色接管”“完整 V 自动化才能交付”“每轮 HTML”一律不得作为当前任务来源。已有安全契约与真实失败仍保留。
4. 工具无法表达新范围时，不修改旧台账使其变绿；先复用已有证据形成新范围逐项验收。只有妨碍必要验证的真实工具缺陷才最小修复。
5. 每次交接区分产品缺陷、工具缺陷、环境阻塞和后续范围；不把设备不可用变成持续扩建工具的理由。
6. 活跃旧会话必须先读取新 START-B/START-C 再继续；文件更新不会自动改变已运行会话的上下文，需用户转交启动提示词。

初始任务状态均为“未按本计划签收”；先认领已有成果再补缺，不代表全部从零开发。R1 支持表和 R2 主机准备可并行，R3 按单元提前推进，只有最终签收等待全部 Must 通过。
