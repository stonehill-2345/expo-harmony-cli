# 官方优先、mapping 补充设计规范

- 日期：2026-09-09
- 状态：按用户确认的简化方向修订，待实施
- 范围：当前 CLI 的 Harmony 原生插件链接

## 1. 固定处理规则

**官方优先，未覆盖时自研补充，仍未覆盖则提示 skill。**

```text
项目实际依赖
  -> 官方 link-harmony 写入临时目录
  -> 官方已覆盖插件保留官方注册
  -> 官方未覆盖插件查询 HARMONY_PACKAGE_MAPPING
  -> 命中则补充自研注册，未命中则提示 skill
  -> 合并后复用现有检查与事务写入
```

- 不提供模式选择、策略参数或相关环境变量。
- 单个插件未被官方覆盖，不影响其他插件使用官方结果。
- 官方整体不可用时，丢弃临时结果，将全部命中 mapping 的插件交给现有生成器一次批量生成。
- 两者都未覆盖的插件不生成注册；其他成功插件继续处理，并明确报告缺口。
- mapping 长期保留。官方成功时不使用该插件的 mapping 注册字段；官方失败时仍可兜底。
- 同一个插件只注册一次，不以 mapping 字段与官方产物的逐字差异判定失败。

## 2. 实现边界

当前自研生成器、同步入口、managed-state 和原子写入是改造基础。

参考项目仅用于研究，不引入其运行时依赖，也不复制整套实现：

| 参考项目 | 借鉴内容 |
| --- | --- |
| expo-harmony | metadata 处理、临时输出隔离、产物检查思路 |
| Expo-Harmony-Toolkit | 调用项目安装的官方命令、向官方结果补充缺口注册 |

首期不增加完整 scanner、双 descriptor 体系、通用代码解析器、独立发布系统、覆盖率阈值或 mapping 生命周期。官方输出兼容转换（normalization）延后，只有真实案例证明必要时再最小化处理。

## 3. 官方调用与覆盖识别

从用户项目解析实际安装的 RNOH CLI 并记录版本，使用经真实 fixture 验证的 `commandLinkHarmony.func`。不把其他参考项目版本的行为直接套用到当前版本。

一次性契约验证必须覆盖：

- `func([], {}, rawArgs)` 的导出形状和调用方式。
- `harmonyProjectPath`、`nodeModulesPath` 及输出路径的驼峰键名。
- `includeNpmPackages` 空集合、单包、多包及单元素含 `;` 的实际行为，避免空集合误触发全量扫描。
- 临时 Harmony 输出目录配合真实项目依赖，在 pnpm hoisted、symlink/workspace 下的结果。
- 一个官方包完成注册、一个 mapping 包未被官方覆盖，以及整体命令失败。

优先让官方工具读取真实项目依赖路径，不预先镜像整棵 node_modules，不修改已安装包的 package.json。CLI 只做必要的路径解析和轻量 metadata 读取。

候选包来自实际依赖及 Harmony metadata，不受 mapping 白名单限制。字段、禁用声明及默认值以当前官方版本为准；参考项目的扩展字段不能直接当作 RNOH 标准。

调用成功不等于所有插件已链接。结合 metadata 和实际输出，对所需 HAR、ETS/C++ 注册、CMake target 做存在性检查；只检查插件所需部分，不要求所有插件都有全部类型，也不引入通用语法分析。

纯 JS 和已确认无需原生注册的 alias 包跳过链接。patch、shim 等适配状态不直接决定链接行为，其额外引入的原生依赖仍独立判断；无法确认未知包性质时提示核实。

## 4. 自研补充与产物合并

保留 mapping 已有 HAR、多 Package、namespace、CMake 路径等字段，复用当前取值及渲染 helper，仅为官方缺口生成片段。

- 官方成功时保留三份官方注册文件，只补充缺失的 import、实例、include、子目录和 target。
- 官方整体失败时复用现有批量模板，不维护第二套完整生成器。
- 插入使用已验证的唯一模板锚点，插入后检查所需片段；不将全部官方文件解析后重新渲染。
- 自研片段顺序稳定、去重；跨插件的同名 symbol/target 应报冲突，不能用去重掩盖。
- 官方部分注册的插件不能直接叠加完整 mapping。能够明确归属并替换其残留时才补充；否则明确报错并保留原工程，不能发布重复注册。
- 官方基础产物不可用时丢弃临时结果，批量使用 mapping 并记录原因；单纯漏包不属于整体失败。

## 5. OHPM 与写入归属

root/entry oh-package.json5 由 CLI 合并官方与自研 HAR，修正为真实项目相对路径，保留 npm 包名与 OHPM 包名差异及多 HAR。

**受管归属以 managed-state 持久化的 managed entries 为准，不以本轮扫描结果或 mapping 键集为准。**

- 历史受管项依据确认后的链接结果更新；确认卸载的包清除旧项。
- 首次遇到未记录的同名依赖：值相同可接管，值不同使用现有冲突保护，不能静默覆盖。
- 非受管依赖保留；扫描异常不等同于卸载，不据此删除历史依赖。
- 最终文件与基线作为同一事务写入，失败时复用现有回滚。

官方仅写临时目录，检查普通非空输出文件、JSON5 和路径范围。最终复用 standalone.ts、managed-state 和现有原子替换，不新增一套锁、发布器或基线存储。

## 6. 命令与提示

prebuild、sync、install、uninstall 共用固定链接流程。保留 alias、patch、codegen、跳过原生同步和强制覆盖的既有职责；强制覆盖不改变官方优先顺序。

install 不能因为包未命中 COMPAT_TABLE 就跳过官方识别；带有效 metadata 的新原生包仍应尝试链接。依赖适配与原生链接分开判断。

未覆盖项逐包报告原因，统一提示：

```text
不是所有 Expo / React Native 原生模块都已适配 HarmonyOS；请以 list 输出、生成项目的 docs/HARMONY.md 和 .agent/skills/expo-harmony-adapter/SKILL.md 为准。
```

list 保留清单职责并增加提示，不为列清单执行链接命令；最近链接结果若展示，需标明是上次同步记录。

更新 content/docs/HARMONY.md 和 adapter skill。检查 Hvigor 是否会二次覆盖 CLI 产物，按实际版本配置关闭；文档明确手动安装原生依赖后需要运行 sync。

## 7. 验收

1. 官方独有、mapping 未收录的包成功注册。
2. 官方包、自研包、未覆盖包共存：前两类各注册一次，第三类提示 skill。
3. 同包官方与 mapping 都支持时采用官方字段；官方失败仍可 mapping 兜底。
4. 官方缺失、失败或产物不完整时批量自研补充并报告原因。
5. alias、仅 ETS/C++、多 HAR、缺 HAR、部分注册及冲突处理正确。
6. 用户 OHPM 依赖保留，卸载清理正确，失败回滚且基线不变。
7. 命令入口、只读检查、清单和文档的规则一致。

fixture 用于验证调用契约，不设覆盖率决策门。执行相关测试、类型检查与构建；有 Harmony 环境时做构建验证，未执行时明确报告。链接成功不等同于运行时兼容。
