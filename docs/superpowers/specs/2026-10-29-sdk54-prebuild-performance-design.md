# SDK54 prebuild 性能优化设计 v1

状态：A 批已实施，整体性能目标未达；B 批未启用。本文是 M2 工程生成链路的性能加固设计，不变更历史阶段接受记录。

执行步骤见 [优化计划](../plans/2026-10-29-sdk54-prebuild-performance.md)。约束依据：[工程生成契约](../../harmony-generation.md)、[M2 原设计](2026-10-27-sdk54-m2-generation-design.md)、[本轮模拟器验收](../../releases/2026-10-29-nova16-emulator-acceptance.md)。

## 1. 问题与目标

编译后的 blank 工程两次 prebuild 实测约 322.7 秒、123.0 秒，首次替换时事务目录约 6 GiB。测量期间存在其他构建活动，这两次结果用于发现问题，不作为隔离性能基线，也不推断全部耗时均来自某一个函数。

代码已确认的成本：

- `generationState.ts/readTree` 将文件内容全部装入 `Map<string, Buffer>`；合并同时持有 current、desired、result，并再次读取 stage 后逐文件写入结果。
- `generationTransaction.ts/hashTree` 处理整棵工程，包括构建产物。无变化分支也需要 initial、candidate、提交前 current 检查；替换分支还校验 backup，恢复另有完整性检查。
- `runHarmonyAsync` 每次运行均先 prebuild；`--no-build-cache` 的缓存清理在 prebuild 之后，不能省掉此前对旧构建产物的处理。

目标是缩短重复生成及配置变更后的生成时间、降低内存和临时磁盘占用，并保留 M2 的内容、权限、冲突和恢复保证。完整 default 的 expo-image 适配继续属于 M7.4。

## 2. 数据边界

所有路径均相对 `harmony/`，分类不等于允许删除。

| 数据 | 本轮默认处理 | 说明 |
| --- | --- | --- |
| 受管源码、JSON5、图标、模块注册、归属状态 | 完整保护 | 保留三方合并、内容及权限检测 |
| 用户文件、未知目录、手工修改 | 完整保护 | 无归属证明时采用原保守语义 |
| `expo-modules/`、HAR、兼容 manifest | 完整保护 | 是生成/运行输入及产物契约，不能当缓存跳过 |
| `oh_modules/`、`entry/oh_modules/`、OHPM 锁文件 | 本轮不移出保护边界 | 涉及依赖树与软链，不能套用 node_modules 的排除规则 |
| `entry/src/main/resources/rawfile/` | 完整保护 | 包含 Release 内嵌 JS、资源及用户文件，不能整体当构建缓存 |
| `.hvigor/`、`entry/.cxx/`、`entry/build/` | A 批仍完整保护；B 批候选缓存目录 | 现有 CLI 已将这三处列为显式清理范围，但此事实不授权普通 prebuild 删除或忽略其中的手工文件 |
| 未知模块名、自定义输出目录、候选目录的软链 | 保守路径 | 本轮不通过递归通配扩大缓存范围，不跟随软链目标 |

## 3. 推荐路线：先 A，按实测决定 B

### A 批：优化文件处理，保持事务契约

1. 将树扫描改为文件清单：路径、类型、mode、大小、来源位置。按需读取待合并 JSON、状态文件及发生内容比较的文件；二进制哈希使用流。
2. 合并结果保存“生成内容”或“从旧工程复制”的动作，避免把整棵旧树留在 Buffer 中。未知文件仍逐字节保留，未知 JSON 不额外解析或规范化。
3. staging 已具有目标内容和 mode 时跳过重复写入。大文件优先使用文件系统支持的 copy-on-write 克隆，支持失败时回退普通独立复制。使用独立 inode，避免硬链接导致 stage 写入影响原文件。
4. 只复用同一次稳定扫描内的计算结果；生成、合并、finalize、校验或 chmod 后必须使相关结果失效。mtime/size 仅作诊断，不能作为内容相等的证明。
5. 保留提交前、交换后、恢复时对可变当前树/备份的独立校验，不把 initialHash 当成后续检查结果。最终无变化判定包含文件模式、路径类型及软链文本。
6. 保持 state schemaVersion 1、现有事务阶段、旧日志恢复口径；含 mode 的 hashVersion 2 与早期无 hashVersion 的日志都需回归。

A 批达到性能和安全门槛即可结束本轮。实际发现的主要成本若仍是受保护的整树扫描，应明确报告剩余成本，进入 B 批评估，而不是删除安全检查。

### B 批：条件性缓存分离，先完成设计门

仅在 A 批不足且隔离基线证明上述三处缓存为主要剩余成本时进入。此批会改变保护边界，不能只向 `hashTree` 和 `readTree` 加几个忽略目录。

设计门需先输出并验证：

- **归属与兼容规则**：目录名只是候选条件。已有项目缺乏可靠归属时继续完整保护；将目录内全部内容原样保留，不把未知文件默认为可删除数据。若无法可靠区分人工修改与工具写入，保持该目录的保守处理。
- **读写协调规则**：生成与 CLI 管理的 OHPM/Hvigor 构建共用明确的项目互斥边界；避免 run 持外层锁又嵌套获取生成锁。现有进程锁只覆盖生成，不覆盖外部 DevEco 构建。外部写入无法可靠排除时，不启用需要弱化冲突检测的快速路径。
- **缓存有效性规则**：普通生成原样保留缓存，由工具验证复用；`--clean` 保留完整旧工程备份；显式 `--no-build-cache` 按既有范围失效。验证配置变化后的下一次构建确实使用新值，并比较 prebuild 与后续 build 的合计耗时。
- **提交/恢复规则**：缓存移交必须和源码目录交换一起设计。逐个目录记录相对源/目标、是否已移交及可恢复身份；缓存移动前写持久化意图，移动后同步日志。先列出每个 rename 前后中断时路径存在组合与恢复动作，再实现新协议。
- **恢复保护规则**：未提交失败恢复完整旧树及原缓存；恢复期间遇到人工文件变动、路径身份改变、缺失或源/目标同时存在等歧义，保留两边并报冲突，不能猜测后删除。若要排除缓存内容哈希，需要提出能证明同等人工修改保护的机制并通过负例；无法证明则保留旧检查。
- **版本规则**：新日志必须有独立版本/明确能力字段，读取器保留旧日志分支。禁止用新投影哈希解释旧 candidateHash；实现回滚前需先完成或恢复新格式事务。

B 批的移交恢复表、外部构建并发方案未闭合前，保持 A 批结果，不交付削弱 M2 语义的缓存快速路径。此门是技术验收条件，不是新增用户审批流程。

## 4. 必须保持的行为

- 普通生成保留用户文件、非受管 JSON 字段、600/755 等权限；仅删除失去最后引用且满足原归属条件的受管内容。
- 用户在生成期间修改内容或执行 chmod，仍可检测并保留修改；不能仅保护已知受管路径。
- 完全相同的输入及当前工程不替换目标目录。配置、资源、插件、有效模块图变化照常生效。
- clean、无状态迁移仍提供完整可恢复备份；进程退出、磁盘空间不足和复制失败不破坏旧工程。
- 状态/模板/受管路径的软链拒绝规则、未知软链按链接保留规则不变。
- 消费端不修改 node_modules 或 HAR 来源，不运行 Python 转换，不新增跨进程持久哈希缓存或公开调优开关。

## 5. 性能目标和判定

以下是本轮建议验收目标，不是原阶段的既有门槛，也不是已测结果。先固定隔离基线；若目标不可达到，报告差距与具体原因，不在结果产生后偷偷放宽门槛。

| 指标 | 建议门槛 |
| --- | --- |
| 编译后无变化重复 prebuild | 中位数较同环境基线下降至少 80%，且不超过 30 秒 |
| 编译后仅改变一项合法配置 | 中位数下降至少 70%，且不超过 45 秒；生成内容正确 |
| 首次生成 / 无构建产物重复生成 | 中位数回退不超过 max(基线的 20%，2 秒) |
| prebuild + 下一次增量构建 | 合计中位数不回退超过 max(基线的 10%，2 秒)，不得将成本转移到重新编译 |
| 大文件内存 | 未参与合并的文件按流/独立复制处理；峰值内存不随其总字节量线性增长，报告 RSS 与 Node external/arrayBuffers 数据 |
| 临时磁盘 | 记录逻辑大小与实际分配大小；克隆不能宣称逻辑复制字节为零，跨文件系统回退单独报告 |

每个场景预热一次、正式顺序执行五次，报告全部样本、中位数和最大值。首次未预热结果另列，不把五次样本包装成可靠的 P95。每次从同一快照恢复，记录机器/工具版本、源码和候选包指纹、文件数/字节数、其他编译进程；基线与优化版本交错测量，避免温度或缓存偏差。

## 6. 完成定义

性能门槛、原 M2 安全回归、真实候选消费与模拟器运行共同通过才记为完成。功能通过但性能未达标记为部分完成；A 批已达标则不扩张到 B 批。历史 M2 记录原样保留，本轮单独形成性能加固报告。

## 7. 2026-10-29 A 批实测后的 B 批判定

A 批已实现按需文件内容、流式摘要、独立复制、未变文件的时间戳保留，以及最多 8 路的文件哈希。并行只发生在一次树扫描内部，摘要顺序及每个事务检查点不变。带诊断的真实 Debug 工程仍是分钟级，不能关闭 30 秒目标。

真实快照中，`oh_modules` 有 70,978 个文件，约 699 MiB；三个候选缓存目录合计仅 1,613 个文件，约 2.37 GiB。逐文件成本不能简单归因于三处构建缓存。OHPM 树属于本设计明确要求完整保护的输入。

B 批未启用，原因是设计门仍不成立：

- 现有工程没有逐文件的缓存归属记录；目录名称不能证明其中不存在人工文件。
- 生成锁不能约束外部 DevEco/Hvigor 写入；增加 CLI 外层锁也不能证明外部写入已停止。
- 仅 rename 缓存或复用 inode 身份，无法检测同 inode 的人工字节修改，不能替代原完整校验。

因此没有更改日志版本、没有移动缓存、没有弱化恢复指纹，也没有向旧工程自动启用快速路径。若后续继续 B 批，必须先证明外部写入协调与人工修改保护，再完成此前规定的逐步移交/恢复表及故障验证。当前状态为 A 批功能与资源优化落地、整体性能验收未完成；不宣称目标已达。
