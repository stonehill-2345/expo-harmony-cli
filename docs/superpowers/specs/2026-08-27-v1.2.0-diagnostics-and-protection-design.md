## 0. 背景与目标

路线图原 1.1.0 主题"诊断与变更保护"未随 1.1.0 发布实施（该版实际发布排障修复），整体顺延至 v1.2.0。本版目标：

1. **失败前置化**：用户在链路早期（而非 ohpm install / DevEco 构建时）发现环境缺失；
2. **防数据丢失**：`sync`/`prebuild` 覆盖 CLI 托管文件前检测用户手改，静默覆盖变为显式阻断；
3. **心智收敛**：`doctor` 一条命令汇总环境、项目、漂移三个诊断源。

**不做**（维持悬置）：JSON 报告、统一 bundle 命令、产物 hash/stale、任何构建类功能（`build-hap` 属 v1.3.0）。

## 3. 受管文件保护（drift）

### 3.1 状态扩展：ManagedState v1 → v2

```ts
export type ManagedState = {
  version: 2;
  packages: Record<string, ManagedPackage>;            // 既有，结构不动
  generatedFiles?: Record<string, {                   // 新增：A 类基线（整文件 hash）
    contentHash: string;                              // sha256，与既有 ManagedFile 同算法
    cliVersion: string;                               // 写入时的 CLI 版本
  }>;
  managedEntries?: Record<string, {                   // 新增：B 类基线（托管条目写入值）
    path: string;                                     // oh-package.json5 相对路径
    dependency: string;                               // 托管依赖名
    spec: string;                                     // 上次 CLI 写入的值（file:... 形式）
    cliVersion: string;
  }>;
};
// managedEntries 键格式：`${path}:${dependency}`（冒号不出现在路径与包名中，可逆唯一）
```

**v1 -> v2 迁移规则**：

1. `readManagedState()` 读取 v1 文件时**归一化为 v2 内存形态**（`version: 2` + 原 packages 原样保留 + `generatedFiles` 缺省为无基线），落盘发生在下一次任何写入（read -> mutate -> write 链路）时，因此 `recordManagedPackage`/`recordGeneratedFileBaselines` 首次写入均天然落 v2；
2. `generatedFiles`/`managedEntries` 形状校验：JSON 合法但字段形状错误（如 `contentHash`/`spec` 非字符串、条目非对象、generatedFiles **键**或 managedEntries 的 `path` **不是安全相对路径**）时**丢弃整个对应字段**（等效无该类基线，sync 放行并重建，见 3.2 退化语义），避免"比对恒不等 -> 永久 drift 阻断且用户无解"或访问项目根之外的路径；packages 字段不受影响。安全相对路径 = 非 `..` 起始、`path.resolve(projectRoot, key)` 仍位于 projectRoot 内（symlink 指向项目外不单独处理，记为已知边界--仅读比对、无写入无外泄）；
3. 旧 CLI 读 v2 文件会走既有 `version !== 1` 回退为空状态，`cleanupManagedPackage` 不删任何文件--降级场景向安全方向退化，可接受；
4. JSON 解析失败（文件损坏）沿用既有"视为空状态"降级。

### 3.2 保护范围

A 类清单从 `runAutolinking` 返回的 `files` 数组派生并**排除 `oh-package.json5`**（不手维护第二份清单）；B 类只比对托管条目本身：

- **A 类（整文件覆盖，记整文件 hash）**：
  - `harmony/entry/src/main/ets/RNOHPackagesFactory.ets`
  - `harmony/entry/src/main/cpp/RNOHPackagesFactory.h`
  - `harmony/entry/src/main/cpp/autolinking.cmake`
- **B 类（合并写入，逐条比对、持久化条目基线 managedEntries、不记整文件 hash）**：根/entry `oh-package.json5` 中 CLI 托管依赖条目的**三态判定**（现值 = 磁盘上的 spec；期望 = 当前映射派生的 `file:...` 值；基线 = managedEntries 记录的上次 CLI 写入值）：
  1. 现值 = 期望 → 通过；
  2. 现值 ≠ 期望，且现值 = 基线记录值 → **CLI 升级/映射变化的合法 spec 变化**，放行覆盖（与 A 类"升级不误报"哲学对齐）；
  3. 现值 ≠ 期望，且现值 ≠ 基线记录值 → **用户手改**，阻断；
  4. 无该条目基线记录（迁移/早期状态）→ **形状退化**：现值仍属 `file:` 家族（`file:...node_modules...`）放行，脱离 file: 形式（如 `1.0.0`）阻断；
  5. 现值为 undefined（条目被删）→ 放行，sync 重建（托管条目由合并逻辑必然回写）。

  **unmanaged 条目（不在托管映射中的依赖）的任何修改不触发阻断**--既有保留逻辑照常回写，无 drift。B 类不再借用"A 类基线存在"作前置开关--managedEntries 即 B 类自身基线，无记录时走形状退化。

### 3.3 写入流程（挂载于 standalone.ts 的 syncHarmonyAutolinking 咽喉处）

```text
0. 残留检查与恢复（上次进程在事务中途被强杀的场景）：
   扫描本次受管文件路径与 managed-state.json 的 *.cli-tmp / *.cli-bak 残留：
   - .cli-tmp（任何阶段残留）→ 无独立价值，自动删除 + info 提示；
   - .cli-bak 且目标文件不存在 → bak 是原文件唯一副本，自动 rename 回原名
     （info 提示"已恢复上次中断的备份"），随后流程照常；
   - .cli-bak 且目标文件存在 → 无法机判新旧取舍，**阻断**并列出文件与两种处置：
     确认磁盘新内容可接受 → `sync --force`（force 路径自动清理全部残留并重建基线）；
     需要旧内容 → 手动将 bak rename 回原名后重跑。
   `--force` 下不做阻断，仅清理全部残留（用户已明示放弃保护）。
   绝不静默覆盖可能仍有价值的 .cli-bak。
1. 渲染出即将写入的 files（既有逻辑；runAutolinking 为纯计算，不落盘）
2. A 类逐文件比对：磁盘内容 hash ≠ 记录 hash（记录存在时）→ 收集为 drift
3. B 类比对（managedEntries 三态判定，见 3.2；无基线记录时形状退化，
   首次执行同样放行建基线）
4. 有 drift 且未 --force → 抛 DriftError（不落盘）：
   - 列出被改文件相对路径
   - 提示 "git diff <file>" 查看改动
   - 指引：确认无需保留后 sync --force / prebuild --force
5. 通过 → 五阶段事务写入（暂存 + 备份 + 替换 + 状态落账 + 清理；c/d 阶段失败共用同一回滚实现）：
   a. **暂存**：每个文件先写同目录 `<name>.cli-tmp`；任一写失败 → 清理全部 tmp、
      原文件未动、状态未写，干净失败；
   b. **备份**：已存在的目标文件先 rename 为 `<name>.cli-bak`（新建文件无备份）；
   c. **替换**：逐个 rename `tmp → 目标`（同目录 rename，原子且几乎不失败）；
      任一失败 → **逐个回滚**已替换文件（删除新内容、`bak rename` 回原名），
      清理剩余 tmp 与 bak；回滚全部成功 → 报错（磁盘 = 执行前状态，基线未动，
      下次普通 sync 直接通过）；回滚也失败 → 报错并明确提示 sync --force
      （唯一残留出口，此时磁盘为半完成态）；
   d. **状态落账（原子，先于删 bak）**：内存中**一次合成完整新 state**（A 类 hash +
      cliVersion、B 类 managedEntries 期望值，A/B 不分两次落盘——
      第一次成功第二次失败同样造成基线与回滚后磁盘不一致）→ `writeManagedState`
      写 `managed-state.json.cli-tmp` 后同目录 rename 落盘；任一步失败 →
      走与 c 相同的回滚（文件回到执行前、旧基线未动，报"可直接重跑"）。
      **禁止"先删 bak 再写 state"**——state 写失败会留下"新文件内容 + 旧基线"
      的自造 drift 死锁，下次普通 sync 被 CLI 自己阻断；
   e. **清理**：state 确认持久化成功后才删除全部 bak；此步失败仅 warn
      （文件与基线已一致，残留 bak 不破坏一致性）
```

prebuild 与 sync 均经过此咽喉，一处生效全覆盖。**force 透传链必须完整**：`runHarmonyGeneration(projectRoot, exp, { force })` 内部调用 `syncHarmonyAutolinking(projectRoot, { force: opts.force })`（第二参为具名类型 `SyncAutolinkingOptions`，见 1.1，杜绝参数错传）——prebuild --force 删除 harmony/ 重建后，残余的 v2 基线（状态文件在 `.expo-harmony/`，不随 harmony/ 删除）与新建内容 hash 必然不同，若 force 未透传会误抛 DriftError。必须补测试："已有 v2 基线 + prebuild --force 成功"。

### 3.4 特殊场景既定行为

| 场景 | 行为 | 依据 |
|---|---|---|
| 无记录 + 文件存在（新 clone/CI 首次） | 不阻断；info 提示"首次建立受管文件基线"；写入并记录 | gitignore 基线的已接受代价 |
| CLI 升级导致生成内容变化（A 类） | 磁盘 hash 与旧记录一致 → 非 drift，正常覆盖并更新记录 | 记录式方案核心优点，杜绝升级误报 |
| CLI 升级/映射变化导致 B 类期望 spec 变化 | 现值 = managedEntries 基线记录值 → 合法变化放行覆盖（3.2 规则 2） | 与 A 类哲学对齐 |
| `--force` | 跳过阻断直接覆盖，写入后基线同步更新 | 主公决策 |

### 3.5 `--force` 语义统一

- `sync --force`：新增，跳过 drift 阻断，**只覆盖受管文件、保留 harmony/ 其余内容**；
- `prebuild --force`：既有"映射为 expo prebuild --clean + 删除整个 harmony/ 重建"的**破坏性完整重建**语义不变——**删除整个 harmony/，包括签名、资源和用户手工配置**，仅同时跳过 drift 阻断。该产品风险必须在**三处显式警告**（缺一不可）：
  1. **命令输出**：删除 harmony/ 前打 warn"将删除整个 harmony/ 目录（含签名、资源与手工配置），此操作不可恢复"；
  2. **guide.md**：与 `sync --force` 的局部覆盖对照说明（已有，保留）；
  3. **CHANGELOG**：行为变化条目中置顶强调破坏范围；
- 两语境下 `--force` 都表示"放弃保护"，但破坏范围不同（sync 局部 / prebuild 整目录），由文档明确区分。

### 3.6 install/uninstall 前置 drift preflight

`install`（[installer.ts](src/installer/installer.ts)）与 `uninstall`（[uninstaller.ts](src/installer/uninstaller.ts)）的自动 sync 位于**一系列不可逆动作之后**（expo install / pnpm install / 卸载依赖 / cleanupManagedPackage 改写 package.json 与状态）。drift 在最后一步才抛错会留下半完成状态且无恢复入口。

规则：

- 两命令在**任何变更动作之前**执行只读 drift preflight（抽 `assertNoDrift(projectRoot)`：与 sync 咽喉同一判定实现 `collectDrift`，含 B 类三态与形状退化）。**位置要求**：install 必须位于 `ensureReactNativePermissionsPlugin`（可能修改 app.json）之前，即参数校验之后的第一步；uninstall 位于依赖卸载之前；
- 有 drift 时立即失败（exit 1），提示"先 `sync --force` 或还原手动修改再重试"--此时 package.json、node_modules、managed-state 均未被本命令改动；
- `install/uninstall` 新增 `--force` 透传给内部 sync，作为绕过入口；
- 测试断言：drift 触发失败后，package.json 快照、managed-state 快照、受管文件内容均与执行前一致。

## 4. doctor 命令

**项目根必须存在**（缺 package.json = fail 退出 1，提示 cd 到项目根）。三段输出：

```text
▸ doctor：项目与环境诊断

环境（复用 env 注册表，仅计数）   ✓ 4 / ⚠ 2 / ✗ 0
项目
  ✓ harmony/ 工程存在
  ⚠ 依赖基线偏离：react-native 0.76.5 ≠ 验证基线 0.77.1（未验证组合）
  ⚠ 受管文件漂移：2 个文件被手动修改，下次 sync 将被阻断
汇总：可继续开发，但有 3 项警告。下一步：处理漂移文件（sync --force 或还原），见上文清单。
```

project-checks 三项（doctor 专用）：

| 检查 | fail/warn | 说明 |
|---|---|---|
| harmony 存在性 | 缺失 = fail | hint 指向 `prebuild --platform harmony` |
| 基线比对 | 偏离 = warn | 比对 version-matrix.ts 的 react/reactNative/expo/rnoh；只报不拦；**package.json 解析失败 = warn**（"无法解析依赖清单"），doctor 自身绝不因项目文件异常而崩溃 |
| drift 现状 | 有 drift = warn | **A + B 等价只读检查**：A 类读 managed-state 基线键比对；B 类调用 `runAutolinking`（纯计算不落盘）取 `managedOhPackageEntries`，按 3.2 三态+形状退化与 sync 同一判定实现（collectDrift）——doctor 与 sync 同一数据源，杜绝"doctor 报无漂移、sync 却阻断"的裂缝。runAutolinking 调用整体 try/catch，node_modules/oh-package 缺失或解析异常降级 skip（"无法计算托管条目期望"）；无基线 -> ok（"下次 sync 将建立"）；注明"下次 sync 将被阻断"；阻断职责在 sync，doctor 只汇总 |

## 5. 退出码分级

| 码 | 含义 | 适用 |
|---|---|---|
| 0 | 全部通过（含 skip） | env / doctor |
| 1 | 存在任一 fail | env / doctor；及现有全部命令异常路径（不变） |
| 2 | 无 fail 但有 warn | env / doctor |

实现：`dispatch()` 保持 void 返回；env/doctor 内部直接设 `process.exitCode`，且**入口首行重置为 0**——`process.exitCode` 是进程级全局，同进程内程序化多次调用（测试、embedder 复用 dispatch）时，上一次设置的 1/2 会残留并被后续普通命令继承；重置后每次 env/doctor 独立结算自己的退出码。`main()` 的 catch-exit-1 不动，其他命令退出语义零变化。

## 6. 错误处理与边界

- `probeCommand`（src/utils/exec.ts 新增）：任何 spawn 失败返回 `{ ok: false, stdout, stderr }`，绝不抛出；Windows .cmd 解析复用 `resolveCommandInvocation`；
- **状态原子写的 rename 替换语义（Windows）**：`writeManagedState` 的 `managed-state.json.cli-tmp → managed-state.json` rename 是唯一"目标已存在"的 rename——Unix 同目录 rename 原子替换，Windows 依赖 MOVEFILE_REPLACE_EXISTING，且目标被占用（杀毒扫描、编辑器打开）时抛 EPERM/EACCES/EBUSY。统一经 `renameAtomic`（src/utils/atomic-rename.ts）：win32 下这三类错误立即重试（最多 3 次）后仍失败才抛错（走 3.3 步骤 5d 回滚）；其余平台与错误直接抛。受管文件的备份/替换/恢复 rename 目标位置均已被腾空或不存在（先备份后替换、恢复时目标缺失），无覆盖语义，直接 renameSync；
- 上次进程强杀的 `*.cli-tmp` / `*.cli-bak` 残留由 3.3 步骤 0 统一处理，不进入正常写入路径；
- DriftError 为普通 Error 子类，走 main() 既有 catch 路径；`--force` 在命令层解析后按 `SyncAutolinkingOptions`（1.1）以 `{ force }` 传参给 `syncHarmonyAutolinking`，且 `runHarmonyGeneration` 内部必须透传 `opts.force`（见 3.3 透传链）；
- 非 TTY（CI）无交互路径，全依赖退出码与 `--force`；
- env 在非项目目录运行不报错（pm 置 skip）。

## 7. 测试策略

- **env-checks 单测**：每检测独立，mock `probeCommand`/fs；覆盖缺失、版本过低、输出解析异常三类；
- **drift 单测**（临时目录 fixture）：
  1. 手改 A 类文件 → sync 抛 DriftError 且文件未被覆盖；
  2. `--force` → 通过且基线更新；
  3. 磁盘内容与记录 hash 一致、但与新生成内容不同（CLI 升级场景）→ 不阻断、覆盖并更新基线；
  4. 无记录首次 → 放行 + 建基线；
  5. oh-package managed 条目被改 → 阻断；
  6. B 类合法升级（现值=基线 spec≠期望）→ 放行覆盖并更新基线（3.2 规则 2）；
  7. 无 B 类基线的形状退化：改为 `1.0.0` 阻断、改为其他 `file:` 值放行；
  8. 替换阶段 rename 失败 → 回滚成功后全部文件恢复原内容、无 tmp/bak 残留、基线未动，普通 sync 可直接重跑（3.3 步骤 5c）；
  9. 状态落账失败（mock：拦截 managed-state.json 的 tmp→rename 抛错）→ 同一回滚：全部文件恢复原内容、旧基线未动、无 tmp/bak/state-tmp 残留、普通 sync 直接通过（3.3 步骤 5d，防"新文件内容 + 旧基线"自造死锁）；
  10. **启动时残留检查**（3.3 步骤 0）：残留 .cli-tmp → 自动清理后正常写入；残留 .cli-bak 且目标文件缺失 → 自动恢复原文件后正常写入；残留 .cli-bak 且目标文件并存 → 阻断并列出残留与双出口（--force / 手动恢复），`--force` 后清理残留并重建基线——绝不静默覆盖 .cli-bak；
  11. **renameAtomic**（win32 语义）：mock renameSync 前两次抛 EPERM 第三次成功 → 最终成功；三次全失败 → 抛错且原文件未动；
- **doctor 组合测试**：mock 注册表验证分段输出与 0/1/2 三种退出码；
- **退出码状态隔离**：同进程先跑得 2 的 env（或 doctor），再跑全绿的 env → 第二次 `process.exitCode` 为 0（入口重置生效，程序化多次调用不互相污染）；
- **Windows 验证**：CI matrix 含 windows runner（renameAtomic 重试与 writeManagedState 原子性、残留检查在 win32 跑全量）；暂无 Windows CI 时列入发布前手动验证清单（vitest 全量 + env/doctor/sync 冒烟）；
- **回归**：standalone/sync 既有测试补 state 写入断言；全量 vitest + type-check + create→install→prebuild 冒烟。
