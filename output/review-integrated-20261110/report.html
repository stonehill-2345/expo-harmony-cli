P1 1. 备份清理失败后，事务回滚会丢失目标文件

apps/cli/src/sdk54/file-transaction.ts:61

两个目标文件均已替换；第一个旧备份删除成功，删除第二个备份抛出 I/O 错误。清理仍在 commit 的 try 内，catch 随即删除两个新目标并尝试恢复旧备份。

影响：第一个旧备份已经不存在，新文件又被回滚删除，导致该文件彻底消失。隔离复现中 a.json 不存在、b.json 恢复原值。此问题在合并前已存在，本次再次确认。

修复方向：将“提交成功”与“提交后的备份清理”分离；清理失败不可再执行依赖已删除备份的回滚，并补第二个备份清理失败的故障测试。

证据：transaction-data-loss；真实 TypeScript 实现转译，仅注入 fs 清理 EIO。

P1 2. 新增 Screens 测试使仓库必跑检查失败

scripts/sdk54/__tests__/screens-harmony-boolean.test.mjs:27

测试用 createRequire 绑定临时入口，再 require("./utils.cjs")。源码归属扫描把此相对字面量归到测试文件目录，因此无法解析。

影响：OWN-01/03/04/05/06 与 OWN-07 两项失败，pnpm check 在 SDK54 工具阶段中断；这不是缺少解析器安装，工具 setup 已完成。

修复方向：使测试动态加载位置与静态扫描规则兼容，保留归属扫描完整性；修复后运行这两项并重跑总检查。

证据：完整检查日志，Unresolved static source references: screens-harmony-boolean.test.mjs:29 ./utils.cjs。

P2 3. 稀疏提交未检查父目录符号链接，可写出 Harmony 目录

packages/expo-modules-autolinking/src/platforms/harmony/generationTransaction.ts:450

新 managed-patch 路径只对最终文件做 lstat/内容指纹检查。若生成后、提交前，entry 等父目录被并发替换成指向外部目录的符号链接，且外部目标与 before 指纹相同，检查仍通过。

影响：通过 after-backup 故障钩子在临时目录精确模拟此窗口：事务成功，harmony 外的文件从 before 变为 after，原目录中的文件仍为 before。它违反生成器的写入边界；不是普通无并发运行必然触发。

修复方向：提交和恢复都需要验证根目录与路径各级祖先，拒绝符号链接/目录身份变化；把父目录替换纳入事务冲突测试，不能只依赖生成阶段的检查。

证据：sparse-parent-symlink-escape；临时项目和外部文件均为复现专用，已清理。

P2 4. E2E 超时只发 SIGTERM，无法保证结束

scripts/sdk54/ai-e2e/process.mjs:48

timeout 和 abort 都只发送一次 SIGTERM，随后无限等待 child 的 close 事件。对忽略 SIGTERM 的构建/测试进程，没有宽限期后的强制终止。

影响：配置 500 ms 超时，1600 ms 后 Promise 仍未返回；复现程序最后向自己创建的进程组发 SIGKILL 才完成。正式 runner 可一直挂住，无法落盘该用例结果和关闭报告。

修复方向：保留部分日志，设置有界终止宽限期，随后终止本次进程组并回收；同时覆盖忽略 SIGTERM 的超时/取消负例。

证据：timeout-does-not-bound-process，实际用时约 1610 ms，最终退出信号来自复现程序。

P2 5. 独立证据重算仍信任 PASS 标记，可接受无效证据

scripts/sdk54/ai-e2e/report.mjs:91

verifyResultIdentity 检查状态、时间戳和超时标记，却不核对已保存 command.exitCode；verifyEvidence 只检查截图魔数，candidate 只验文件 hash。使用仓库测试相同结构，9 字节“PNG”、空 packages 候选、普通文本 device-assertion 就能 canClose=true；再写入 command.exitCode=17，仍无错误。

影响：报告无法按承诺从落盘命令/证据独立重算结论。截断截图或互相矛盾的状态会被接受。正常 runner 在执行时确实按 exitCode 计算状态，因此这针对独立报告校验，不代表正常失败命令必然被 runner 写成 PASS。

修复方向：校验 PASS 与命令结果一致、候选满足阶段 schema、图片具有有效结构/尺寸；定义 device-assertion 的可重放契约，而不把文件存在和 hash 一致等同于断言通过。

证据：invalid-evidence-accepted / failed-command-accepted；errors=[]，canClose=true。

scripts/sdk54/a-m7-entry-gate.mjs:43

implementationReady 只合取 A06、证据有效和 M6.closed；M4/M5/V 虽然进入 blockers，却没有进入 ready 判定。

影响：构造 M6 关闭、M4/M5/V 未关闭且存在 ExpoImage 发行项的输入，会同时输出三个 blocker 和 READY_FOR_FORMAL_INTEGRATION。当前真实输入仍 BLOCKED，这是潜在门禁误放行。

修复方向：让 ready 取决于全部必需前置，与 blocker 列表保持一致，并测试互相矛盾的阶段状态。

证据：gate-upstream，本次复跑再次通过缺陷断言。

P2 7. A-07 捕获冻结台账冲突后，仍标记证据有效

scripts/sdk54/a-m7-entry-gate.mjs:70

calculated 在 deepEqual 校验前赋值。冻结台账与重算结果不同会进入 catch，但 calculated 未清空，随后 stageEvidenceValid=Boolean(calculated) 仍为 true。

影响：即使已记录 Frozen stage progress differs 错误，也不会生成 STAGE_EVIDENCE_INVALID，仍可能返回 READY_FOR_PACKAGE_IMPLEMENTATION。复现用哈希有效的合成接受记录与冲突冻结台账；未改真实台账。

修复方向：使用独立的校验成功标志，只有重算和冻结一致性都成功才有效；任何校验异常都阻断进入。

证据：gate-frozen-mismatch。
