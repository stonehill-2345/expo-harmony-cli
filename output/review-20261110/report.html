P1备份清理失败会导致事务目标文件丢失

apps/cli/src/sdk54/file-transaction.ts:61–71 · 既有代码 · 工程链路 / B

事务已写入所有新文件后，仍在同一个 try 中逐个删除旧备份。如果第一份备份删除成功、第二份删除发生 I/O 错误，catch 会删掉所有已写入目标，再尝试恢复备份。第一份旧备份已经不存在，目标文件便永久丢失；finally 还会继续清理备份。

复现：在独立临时目录对两份 JSON 文件执行真实事务实现，仅向第二次备份删除注入 EIO。结果 a.json 不存在，b.json 恢复为旧值。调用点 install-patches.ts:100 用该事务写入 patch、许可证和 package.json，因此这是实际安装链路的数据保护缺陷。复现只操作临时文件，未破坏工作区。

修复方向：明确提交点，把提交后的备份清理从回滚区间分离；清理失败应保留新文件和可恢复备份。回滚恢复失败时也不能在 finally 中删除唯一备份。补充“部分备份已删”和“恢复 rename 失败”故障测试。

P2A-07 捕获台账不一致后仍把证据标为有效

scripts/sdk54/a-m7-entry-gate.mjs:70–77 · A 新增门禁

P2Harmony Metro 分支绕过项目自定义 resolver

packages/@expo/metro-config/src/withHarmony.ts:64–70 · 既有代码 · M5 / B

函数保留了原始 config.resolver.resolveRequest，却仅在非 Harmony 分支调用它。Harmony 直接走 RNOH resolver，其默认回退使用 context resolver，不会执行原项目函数。依赖自定义别名、模块替换或 resolver 插件的项目会出现 iOS 正常而 Harmony 解析失败的情况。

复现：转译执行实际 withHarmony 源码，并加载本机已安装的真实 RNOH Metro 配置。自定义 resolver 把 my-business-alias 指向 /custom/…；iOS 正确返回该地址，Harmony 返回默认地址，且自定义 resolver 调用次数为 0。

修复方向：组合项目 resolver 与 Harmony 适配器，明确回退顺序并避免递归；增加同一配置下 iOS/Android/Harmony 与自定义别名的行为测试。这属于总规划明确要求的 M5 能力，不能由 blank 能运行代替。

P1：应优先解决的数据保护或必跑检查阻断；P2：正常集成场景下的行为／验证缺陷。复现脚本：reproduce-findings.mjs；结构化实际输出：reproduced-findings.json；ownership 失败见 pnpm-check.log。
